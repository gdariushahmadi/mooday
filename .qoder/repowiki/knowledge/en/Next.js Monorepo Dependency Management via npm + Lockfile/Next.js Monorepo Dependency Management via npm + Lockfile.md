## System / Approach

This is a single-package Next.js application (not a true npm workspaces monorepo) that manages all third-party dependencies through **npm** with a **`package-lock.json`** lockfile. The repository uses the standard npm dependency lifecycle: `dependencies` and `devDependencies` in `package.json`, version pinning via caret ranges, and deterministic installs from the lockfile.

There are no private registries, vendored packages, or Yarn/PNPM/Bun lockfiles — only `package-lock.json`. `.gitignore` explicitly excludes `node_modules/`, `.pnp`, and `.pnp.*`, so the install tree is never committed.

## Key Files

- `package.json` — declares runtime deps (`next`, `react`, `react-dom`, `@supabase/supabase-js`, `stripe`, `@sentry/nextjs`) and dev deps (`typescript`, `vitest`, `@playwright/test`, `eslint`, `tailwindcss`, testing libraries). Also pins the Node engine to `>=20.9.0`.
- `package-lock.json` — full lockfile generated by npm; used for reproducible installs.
- `.deploy/package.json` — a duplicate manifest copied into the standalone deployment bundle alongside `.next/standalone/server.js`; it mirrors the root manifest so the deployed server can resolve its own runtime dependencies independently of the source repo.
- `scripts/build-standalone.sh` — builds the app with `next build`, then copies `.next/standalone/server.js` and `.next/standalone/package.json` into `.deploy/` together with `public/` and `.next/static/`. This is how the production cPanel deployment ships dependencies: as a tarball containing the minimal standalone package plus assets, not as a full `node_modules` tree.
- `.vercelignore` — excludes `node_modules` from Vercel deployments, relying on the platform's own install step.
- `.gitignore` — excludes `node_modules`, pnpm/Yarn artifacts, and other transient files.

## Architecture and Conventions

1. **Single manifest, two copies.** The root `package.json` drives development and CI. A near-identical copy lives under `.deploy/package.json` because the Next.js standalone output includes only `server.js` and a stripped-down `package.json`; the script copies both so the deployed process has a valid manifest. Any change to runtime/dev dependency sets should be reflected in both files.

2. **Runtime vs dev split.** Runtime-only packages (`next`, `react`, `react-dom`, `@supabase/supabase-js`, `stripe`, `@sentry/nextjs`) go under `dependencies`. Everything else — tooling, types, test runners, linters — goes under `devDependencies`. This keeps the deployed standalone bundle small.

3. **Version strategy.** Runtime dependencies use caret ranges (`^16.2.9`, `^19.2.4`, `^2.110.5`, `^22.5.0`, `^10.70.0`) allowing patch/minor updates within the major version. Dev dependencies similarly use caret ranges. The `engines.node` field enforces Node ≥ 20.9.0 at install time.

4. **Supabase CLI is invoked inline.** The `supabase:start`, `supabase:stop`, and `test:phase2:db` scripts call `npx supabase@2.109.1 ...` rather than installing it as a project dependency. This pins the Supabase CLI to an exact version per run without polluting the dependency graph.

5. **No vendoring.** There is no `vendor/` directory, no `pnpm-lock.yaml`, no `yarn.lock`, no `.pnp`, and no custom `.npmrc` registry configuration. All packages come from the public npm registry.

6. **Standalone deployment model.** Production deploys do not ship `node_modules`. Instead, `next build --output=standalone` produces a self-contained `.next/standalone/` tree that bundles only the runtime code needed by `server.js`. The deployment script then tars this plus `public/` and ships it to cPanel, where it is unpacked and restarted via Passenger.

## Conventions and Constraints

- **Lockfile is authoritative.** `package-lock.json` is committed and must stay in sync with `package.json`; any dependency change should go through `npm install` to update the lockfile.
- **Node version is enforced.** The `engines.node >= 20.9.0` constraint in `package.json` is checked by npm during install.
- **Dev/runtime boundary is strict.** Only packages actually required at runtime by the built Next.js app belong in `dependencies`; everything else stays in `devDependencies` to keep the standalone bundle lean.
- **Duplicate manifests must stay in sync.** Both `package.json` and `.deploy/package.json` must reflect the same dependency set; the deploy script copies the latter verbatim onto the server.
- **CLI tools are pinned via `npx @version`.** The Supabase CLI is invoked as `npx supabase@2.109.1` inside scripts rather than declared as a dependency, fixing its version per invocation.
- **No private registry or vendoring.** The repo relies entirely on the public npm registry; there is no `.npmrc`, `bunfig.toml`, `pnpm-workspace.yaml`, or vendored `node_modules`.
