The module is split into two sibling concerns under `src/services` and `src/data`. The `services/backend` package defines a stable contract surface in `contracts.ts` — typed interfaces for auth, profiles, addresses, listings, media, seller cards, likes, cart, follows, orders, chat, reviews, reports, disputes, notifications, payment methods, and blocks — aggregated by the `Phase2Backend` interface. `supabase.ts` implements every interface as a `SupabaseXxxService` class backed by `@supabase/supabase-js`, handling DB queries via `.from(...).select/update/insert/delete`, storage uploads to `avatars` and `listing-media` buckets with signed URLs, and Realtime subscriptions for chat and notifications. `config.ts` reads `NEXT_PUBLIC_*` env vars to select between `mock` and `supabase` data sources; `index.ts` exposes factory functions (`getPhase2Backend`, `getPhase3ListingService`, etc.) that return `null` when the corresponding feature flag is disabled, so callers never depend on a live backend being present. Mapper files (`mappers-orders.ts`, `mappers-social.ts`) translate remote rows into UI-friendly records and are re-exported from the index. The `services/admin/actions.ts` file is a separate Next.js Server Actions module marked `'use server'`; it uses a service-role Supabase client to bypass RLS, verifies admin privileges by reading the access-token cookie and checking `profiles.is_admin`, and writes every mutation to an `audit_log` table via a shared `writeAudit` helper. The `data/` directory contains plain TypeScript modules exporting seed fixtures (e.g. `DEFAULT_USERS`, `products`, `orders`, `reviews`, `sellers`, `categories`, `addresses`, `paymentMethods`, `premium-brands`, `seller-profile`, `notifications`, `reports`, `disputes`, `blocked-users`, `my-reviews`, `sales`, `avatar-library`, `mock-images`) consumed by the mock backend or test harnesses; they contain no runtime logic beyond data and small helpers like `generateSessionToken` and email validation.
