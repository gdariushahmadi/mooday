- Each backend capability is exposed as a dedicated interface in `contracts.ts` (e.g. `AuthService`, `ListingService`, `OrderService`) and implemented as a `SupabaseXxxService` class in `supabase.ts`, keeping the contract decoupled from the Supabase implementation.
- Row mapping is done through paired `xxxFromRow` / `xxxToRow` helper functions (used for Address, Listing, SellerCard, Profile) that convert between snake_case Postgres columns and camelCase TS types.
- Mutating services guard user-scoped writes by calling `client.auth.getUser()` and throwing `Authentication required` when no session is present, rather than relying on RLS alone for caller-side checks.
- Storage uploads validate MIME type against `LISTING_MEDIA_ALLOWED_MIME` and enforce size limits (`AVATAR_MAX_BYTES`, `LISTING_MEDIA_MAX_BYTES`) before writing, and perform best-effort rollback of orphaned storage objects when the metadata row insert fails.
- Admin Server Actions follow a uniform pattern: call `getAuthenticatedAdmin()` to derive identity from the Supabase access-token cookie, then wrap every mutation in a `writeAudit` call recording actor, action, target kind, target id, diff, and optional note.
- Feature flags gate backend availability: `getPhase2Backend` and `getPhase3*Service` factories read `getBackendConfig()` and return `null` when the corresponding `mode` / `marketplaceMode` is not `supabase`, so consumers can safely short-circuit without try/catch.
