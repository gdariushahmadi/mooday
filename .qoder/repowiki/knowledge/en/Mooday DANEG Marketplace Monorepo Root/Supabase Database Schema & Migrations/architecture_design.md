The module is a standard Supabase project rooted at `supabase/` with four logical layers:
- Configuration: `config.toml` declares the Supabase project (`mooday`), enables the REST/GraphQL API on `public` and `graphql_public` schemas, configures GoTrue auth (email sign-up, confirmation/recovery templates under `templates/`), and sets search paths.
- Migrations: `migrations/` contains timestamp-prefixed, idempotent SQL migrations grouped by feature phase (phase_2 identity, phase_3 listings/social/orders/admin, phase_4 payment methods/blocked users/notification fanout). Each migration wraps DDL in a transaction (`begin; ... commit;`) and uses `create or replace` / `drop trigger if exists` patterns so they can be re-run safely.
- RLS & Triggers: Tables are created with Row Level Security enabled and policies scoped to `authenticated` vs `anon`, using `auth.uid()` for ownership checks. Business logic is encapsulated in `security definer` PL/pgSQL functions (e.g., `handle_new_auth_user`, `set_default_address`, `fanout_chat_message`, `fanout_order_status`, `fanout_seller_review`) invoked by triggers on `auth.users`, `chat_messages`, `orders`, and `seller_reviews` to enforce cross-table invariants and fan out notifications into a `notifications` table.
- Tests: `tests/` holds per-feature pgtap suites that seed `auth.users` and `public.*` rows, set local roles (`authenticated`/`anon`) with JWT claims, and assert RLS behavior via `is`, `throws_ok`, `lives_ok`, `is_empty`, finishing with `finish()` and `rollback`.
Dependency direction is strictly downward: tests exercise migrations; migrations depend only on `auth` and `extensions`; no application code lives in this scope.
